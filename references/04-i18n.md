# 4 本地化与文案

> 管什么：语言文件清单与推荐基线、键齐平、UTF-8 无 BOM、颜色与样式、可翻译组件与兜底、各版本 API 边界、文案写作口径。
> 上游：`SKILL.md`（结论以此为准）；本文件给出语言表、API 版本边界、判定手法与事故复盘。相关：[03-metadata.md](03-metadata.md) §3.2.3（BOM 判定与写文件命令）、[01-publishing.md](01-publishing.md) §1.3（描述单行规则）、[05-mixin-api.md](05-mixin-api.md)（注入与组件调用）。

本文件里的语言清单、语言数量、键名都是**建议与通用规则**，不是强制标准。每个项目按自己的受众定覆盖范围；一旦定了，就必须在项目内部保持一致。

## 4.1 语言清单：13 种是"推荐基线"，不是强制

**建议做法**：面向玩家的业务模组提供 **13 种**语言文件，路径 `assets/<mod_id>/lang/<code>.json`，全部 **UTF-8 无 BOM**，并且**键集合与 `en_us` 完全一致**。

**最低要求（按项目类型分档，建议而非强制）**：

| 项目类型 | 建议最低覆盖 | 理由 |
|---|---|---|
| 库 / 前置模组（玩家不直接使用） | `en_us` + `zh_cn` | 文案只出现在演示 / 调试界面；多语言收益低，维护成本高 |
| 业务模组（玩家直接交互） | 建议 ≥13 种 | 覆盖面直接影响下载量与评价；但**是否真的做 13 种由项目决定** |
| 纯服务端 / 工具类模组 | `en_us`（+ 服务器管理员语言） | 玩家看不到界面 |

> 这一条是**建议**：13 种不是硬门槛，也不是"少于 13 种就不合格"。反过来，**已有项目保留其已有覆盖，不降级**——已经做了 15 种的不要退回 13 种。额外语言代码以项目自身记录为准，不要凭通用清单反推删减。

### 4.1.1 推荐基线语言表

| 语言 | 语言代码 | 备注 |
|---|---|---|
| 英语（美国） | `en_us` | **基准语言**：新增键一律先写这里 |
| 英语（英国） | `en_gb` | 英式拼写变体，与 `en_us` **分开维护** |
| 简体中文 | `zh_cn` | |
| 繁體中文（台灣） | `zh_tw` | |
| 繁體中文（香港／澳門） | `zh_hk` | 港澳台用語，**与 `zh_tw` 分开维护**（不复用同一份） |
| 文言（華夏） | `lzh` | **翻译重点**：文言文体，用词古雅，禁止现代白话直译 |
| 俄语 | `ru_ru` | |
| 德语 | `de_de` | |
| 日语 | `ja_jp` | |
| 法语 | `fr_fr` | |
| 西班牙语 | `es_es` | |
| 巴西葡萄牙语 | `pt_br` | |
| 韩语 | `ko_kr` | |

**代码有效性依据（已核实，非推测）**：26.3 客户端资源索引 `assets/indexes/34.json`（版本 json 的 `assetIndex.id`）内的 `minecraft/lang/*.json` 清单**同时包含以上 13 个代码**（含 `lzh`、`zh_hk`、`en_gb`）——即游戏能识别、玩家能在语言菜单里选中。

**维护旧版本时必须复核**：按**该版本自己的资源索引**检查 `lzh` / `zh_hk` / `en_gb` 是否存在。缺失的代码游戏不会在语言菜单里列出，写进去也不生效。

```powershell
# 复核某版本可识别的语言代码（先取该版本的 assetIndex.id）
$id = '<assetIndex.id>'
$j  = Get-Content "$env:APPDATA\.minecraft\assets\indexes\$id.json" -Raw
[regex]::Matches($j,'minecraft/lang/([a-z_]+)\.json') |
  ForEach-Object { $_.Groups[1].Value } | Sort-Object -Unique
```

- **判定手法**：把上表代码与命令输出的集合求交；表里有而输出里没有的代码，说明该版本不支持，要么换版本，要么删掉该语言文件（保留会造成"文件在、界面选不到"的困惑）。
- **实际覆盖可以多于基线**：做了 15 种（额外扩展 `en_gb` / `lzh` 之外的语言）是完全正常的。数量只增不减。

## 4.2 配套规则（都是实测踩过的）

### 4.2.1 键必须齐平，缺键比缺翻译严重

- 某个语言文件少键时，游戏会把 **key 原样当文本**显示（实测在聊天里冒出 `message.<mod_id>.blocked` 这样的原始键）。
- 增删键后**逐个语言文件对照 `en_us` 补齐**，不要只补中英两种。
- 判定手法：以 `en_us` 为基准，对每个语言文件求对称差；差集为空才算齐平。

```bash
# 逐语言文件与 en_us 求键集合差（需要 jq）
base=assets/<mod_id>/lang/en_us.json
for f in assets/<mod_id>/lang/*.json; do
  [ "$f" = "$base" ] && continue
  echo "== $(basename "$f")"
  comm -3 <(jq -r 'keys[]' "$base" | sort) <(jq -r 'keys[]' "$f" | sort)
done
```

- **缺翻译 vs 缺键**：缺翻译（有键、值是英文原文）可接受；**缺键**不可接受，因为玩家会看到机器键名。
- 新增键的顺序：先写 `en_us` → 再同步到全部语言文件 → 最后构建。反过来做（先构建后补键）会把缺键带到产物里。

### 4.2.2 颜色不要写进语言值

- **聊天 / 消息类文案禁止在语言值里写旧式 `§` 颜色码**：原版字体渲染器会解析，但第三方 UI 库（如自绘文本引擎）**不解析 `§`** → 颜色静默丢失（实测"红色提示字变白"）。
- 颜色改由**组件样式**给出：`Component.…withStyle(ChatFormatting.RED)`。
- GUI 内的文案一律由**绘制函数的颜色参数**决定（`gui.*` 里历史遗留的 `§a` / `§c` 可保留、不强制清理——已定：**不动**）。

| 位置 | 颜色来源 | 能否用 `§` |
|---|---|---|
| 聊天 / 系统消息 | 组件样式 `.withStyle(...)` | ❌ |
| 物品 / 方块 tooltip | 组件样式 | ❌ |
| 语言值内的 GUI 文案 | 绘制函数颜色参数 | ⚠ 历史遗留可保留，新写的不加 |
| 日志 / 调试输出 | 无（纯文本） | 不需要 |

### 4.2.3 服务端发给客户端的提示必须带兜底

- **现象**：服务端用 `Component.translatable(key)` 发出提示时，翻译在**接收端**解析——接收端没装该模组就会显示原始 key（实测 `message.<mod_id>.blocked`）。
- **修复**：统一改用 `Component.translatableWithFallback(key, 兜底文案)`；兜底文案按玩家客户端语言取（`ServerPlayer#clientInformation().language()`，形如 `zh_cn` / `en_us`），语言文件里没有该语言时回退 `en_us`。
- **兜底顺序（固定四步）**：① 取接收方客户端语言 → ② 在该语言文件里找键 → ③ 找不到回退 `en_us` → ④ 再回退兜底字符串。
- ⚠ **兜底字符串只作为最后手段**，不能替代可翻译组件本身。用 literal 写死文案会牺牲整套多语言（见 §4.3）。

### 4.2.4 描述文案

- 模组列表简介用 `[EN] … [CN] …` 中英双语**单行**（写法见 [01-publishing.md](01-publishing.md) §1.3）。
- 面向玩家的说明（README / 简介 / 更新说明）**英文在前，禁中文独占**。
- 描述里不写会过期的信息（MC 版本、加载器版本、构建日期）。

### 4.2.5 语言 JSON 必须 UTF-8 无 BOM

写文件用：

```powershell
[System.IO.File]::WriteAllText($f, $text, [System.Text.UTF8Encoding]::new($false))
```

判定与完整规则见 [03-metadata.md](03-metadata.md) §3.2.3。

### 4.2.6 经 `expand` 处理的 JSON 禁写转义

语言文件若经 `processResources.expand` 展开，正文里**不要写 `\n`、`\t`、`\u`**——Gradle 的 `expand` 会把它们变成真实控制字符，产出非法 JSON。完整根因见 [03-metadata.md](03-metadata.md) §3.3.5。

## 4.3 事故复盘：一句 `literal` 会让多语言整套失效

### 4.3.1 现象

两条老版本线（1.18.x / 1.19.x）的 jar 装上去，**客户端切成中文也只显示英文**；语言文件本身完全正常（语言文件齐全、`zh_cn.json` 内容正确、也在 jar 的 `assets/<mod_id>/lang/` 下）。

### 4.3.2 根因

这两条分支的 `Component` **没有 `translatableWithFallback`**，当初为了"别让没装模组的客户端看到原始 key"，把提示改成了 **literal（把文案写死进组件）**：

```java
// ❌ 错误做法
return Component.literal(fallback(key)).withStyle(ChatFormatting.RED);
```

`literal` 的内容是**服务端在构建期 / 运行期拼好的固定字符串**，完全绕过了客户端语言表 ⇒ 客户端切任何语言都只会看到那一份写死文案。

### 4.3.3 正确取舍

| 写法 | 装了模组的客户端 | 没装模组的客户端 | 结论 |
|---|---|---|---|
| `Component.literal(写死文案)` | ❌ 永远那一份语言 | ✅ 可读 | **错**，牺牲了整套多语言 |
| `Component.translatable(key)` | ✅ 按自身语言正确显示 | ⚠ 显示原始 key | **老版本线唯一可接受写法** |
| `Component.translatableWithFallback(key, 兜底)` | ✅ 按自身语言正确显示 | ✅ 显示兜底文案 | **首选**（但 1.18.x / 1.19.x 没有此 API） |

**判定规则（通用）**：

1. **能用 `translatableWithFallback` 就用**（1.20.2+ 各线）。
2. 用不了时，**一律退回 `translatable(key)`**，**永远不要用 literal 顶替**——"没装模组的客户端看到 key"是**可接受的降级**，"所有客户端都失去多语言"是**不可接受的回归**。
3. 颜色**不要**写进语言值（旧式 `§` 码会被第三方 UI 渲染器忽略），由组件样式给出：`.withStyle(ChatFormatting.RED)`。

### 4.3.4 修复的交付口径

- 该修复必须以**新版本号**重发受影响版本线的 jar。⇒ 修复必须**重新构建 + 重新部署 + 重新验收**，不许只改文档。
- 版本号后缀必须带连字符（`1.2.0-fix` ✓、`1.2.0fix` ✗），见 [01-publishing.md](01-publishing.md) §1.6。
- 同一修复涉及多条版本线时，**逐条线独立验证**：老版本线没有新 API，写法和其它线不同，不能"改一处就当全线修好"。

### 4.3.5 各分支 API 能力实测（与上面的取舍配套）

| 能力 / API | 边界与实测 |
|---|---|
| `Component.translatableWithFallback` | **1.19.2 不存在**（曾列为未决，现已确认）。1.19.x 只能退 `Component.translatable`（**不得**用 literal） |
| `Component.literal` | **1.18.2 不存在** ⇒ 用 `new TextComponent(String)` |
| 1.18.2 的消息发送签名 | `player.sendMessage(Component, UUID)`；`Commands#performCommand` 描述符为 `(CommandSourceStack,String)I` |
| `ServerPlayer#clientInformation()` | **1.20.2 才引入** ⇒ 1.20.1 分支**没有公开的客户端语言读取口**，该分支兜底固定 `en_us` |
| `Component.translatable(...)` 静态工厂 | 1.19.0 才引入；1.18.x 必须 `new net.minecraft.network.chat.TranslatableComponent("key")` |
| `sendSystemMessage(Component)` | 1.19 改名引入；1.18.x 服务端用 `player.sendMessage(new TranslatableComponent(...), player.getUUID())`，客户端进世界通知用 `player.displayClientMessage(..., false)`（第二参 = 是否 actionbar） |
| `Component` 的 `§` 与样式 | 一律 `.withStyle(...)`，语言值里不写色码 |

**按版本线选写法的速查表**：

| 版本线 | 兜底能力 | 推荐写法 | 禁止 |
|---|---|---|---|
| 1.18.x | 无 | `new TranslatableComponent("key")` | literal / `TextComponent` 写死玩家文案 |
| 1.19.x | 无 | `Component.translatable("key")` | literal 写死玩家文案 |
| 1.20.1 | 无客户端语言读取 | `Component.translatable("key")`，兜底固定 `en_us` | 依赖 `clientInformation()` |
| 1.20.2+ | 有 | `Component.translatableWithFallback(key, 兜底)` | literal |
| 26.x | 有 | 同上 | literal |

### 4.3.6 自查清单（新增分支时逐条过）

- [ ] 提示类组件**不出现** `Component.literal(...)` / `new TextComponent(...)` / `new StringTextComponent(...)` 写死玩家可见文案（**诊断 / 日志除外**）。
- [ ] 语言键在全部语言文件里齐全，且与 `en_us` 键集合完全一致。
- [ ] **实机切换语言验证**：把客户端语言切到简体中文，触发一次提示，确认显示的是中文而不是英文 / key。
- [ ] 语言 JSON 无 BOM。
- [ ] 语言值里没有 `§` 色码（颜色在代码里给）。

## 4.4 兜底实现参考（通用要点）

**推荐结构**：一个统一的文案工具类，按接收方客户端语言解析 + 同语言兜底 + 样式上色。业务代码只调一个入口（如 `blocked(player)`），不散落组件构造。

- 通用要点（可复用）：兜底层必须"**先取接收方语言 → 语言文件里找同语言 → 找不到回退 `en_us` → 再回退兜底字符串**"，且**兜底字符串只作为最后手段**，不能替代可翻译组件本身。
- 老版本线（1.16.5 / 1.12.2 / 1.7.10）没有 `translatableWithFallback`，按同样顺序手写实现，**函数签名与新版保持一致**，便于将来合并。
- 引入工具类时**只新增、不改公开签名**：把调用点从散落的组件构造改成统一入口，但 Mixin 注入签名、方法签名一律不动（注入签名变动会直接导致注入失效）。

### 4.4.1 兜底层的关键判定

| 环节 | 判据 | 失败症状 |
|---|---|---|
| 取接收方语言 | 拿到的值形如 `zh_cn` / `en_us` | 拿到 `null` 或空串 → 一律按 `en_us` |
| 同语言查找 | 该语言文件里有这个键 | 键缺失 → 落回 `en_us` |
| `en_us` 回退 | `en_us` 里有这个键 | 也没有 → 用兜底字符串 |
| 样式 | 颜色由 `.withStyle(...)` 给 | 语言值里有 `§` → 第三方 UI 丢色 |

- **不要用"服务端语言"当兜底依据**：服务端没有"玩家语言"概念，`clientInformation()` 是玩家侧属性。1.20.1 及更早没有这个接口，只能固定 `en_us`。
- **不要在兜底层里做字符串拼接**：把整句拆成前后缀拼接会让翻译无法处理语序差异。要拼接就用带参数的可翻译组件（`Component.translatable(key, args...)`）。

### 4.4.2 组件写法对照（按用途）

| 用途 | 写法 | 说明 |
|---|---|---|
| 玩家可见提示（有兜底 API） | `Component.translatableWithFallback(key, fallback)` | 首选 |
| 玩家可见提示（无兜底 API） | `Component.translatable(key)` / `new TranslatableComponent(key)` | 可接受降级 |
| 带变量的提示 | `Component.translatable(key, arg1, arg2)` | 语言值里用 `%s` / `%d` 占位 |
| 日志 / 诊断 | `Component.literal(...)` 或纯字符串 | **允许**，不面向玩家 |
| 调试界面占位 | `literal` | 允许，但要在发布前确认没进玩家可见路径 |

## 4.5 语言键命名约定（建议）

| 用途 | 建议前缀 | 示例 |
|---|---|---|
| GUI 文本 | `gui.<modid>.*` | `gui.<mod_id>.title` |
| 聊天 / 消息 | `message.<modid>.*` | `message.<mod_id>.blocked` |
| 配置项 | `config.<modid>.*` | `config.<mod_id>.enabled` |
| 物品 / 方块 | `item.<modid>.*` / `block.<modid>.*` | 由注册名派生 |
| 附魔描述 | `enchantment.<id>.desc` | 见 [03-metadata.md](03-metadata.md) §3.1.7 |
| 第三方插件的配置键 | 按插件约定 | 如 `config.jade.plugin_<插件id>.<键名>` |

- **已有项目的键名保持不动**：改键会牵动全部语言文件与第三方翻译平台的映射（平台侧按 key 记录翻译进度，改键等于全部归零）。宁可前缀不规范，也不要为了"统一"改键。
- **新增键按当前约定写**，不要因为"历史键没前缀"就把新键也去掉前缀。
- 键名用小写 + 点分层；不用驼峰、不用空格、不用非 ASCII。

## 4.6 文案写作口径（面向玩家）

| 规则 | 说明 |
|---|---|
| 英文在前 | README / 简介 / 更新说明一律英文在前，中文在后；**禁中文独占** |
| 单行描述 | `description` 单行，用 ` \| ` 分隔多段 |
| 不写会过期的信息 | MC 版本、加载器版本、构建日期不写进描述与 README 正文 |
| 不写流程与规范 | 写作规范、维护规则、AI 流程一律不写进公开文案（内容会原样公开） |
| 不写内部术语 | 分支名、内部分层标记、任务代号对玩家无意义 |
| 措辞稳定 | 同一功能的文案跨版本线照抄基准线，**改一个字也算越界**；确需改动先说明原文 / 改法 / 理由 |

- **移植时文案是"照抄项"而非"重写项"**：与本次版本适配无关的文字，一律照抄基准线。其中相当一部分是作者自己写的措辞。
- **语言值里不出现代码标识**：不要把类名、方法名、配置键直接当文案显示给玩家。

## 4.7 各语言的翻译要点（差异化，不能一份译稿复制 13 次）

13 个语言代码不是"同一段英文的 13 种拼写"。其中若干对之间有**不可复用的差异**，复用会直接产出错译。

| 语言对 / 单语言 | 差异点 | 处理 |
|---|---|---|
| `en_us` ↔ `en_gb` | 拼写变体（`color` / `colour`、`armor` / `armour`、`-ize` / `-ise`） | 两套独立维护；`en_gb` 不是 `en_us` 的复制 |
| `zh_cn` ↔ `zh_tw` | 简体 / 繁体字形 + 用词（`信息` / `訊息`、`默认` / `預設`、`视频` / `影片`） | 转换字形后再校对用词，不能只转字形 |
| `zh_tw` ↔ `zh_hk` | 港澳用語与台湾用語有别（`打印机` / `打印機` / `打印機`、`软件` / `軟體` / `軟件`） | 港澳台三地分开维护；`zh_hk` 不复用 `zh_tw` |
| `lzh`（文言） | 文体古雅，忌现代白话直译 | 用文言句式（`不可`、`欲`、`故`），专有名词保留原名；**不做逐字直译** |
| `ja_jp` | 无空格分词，助词结构 | 长句拆短；不要在日语值里塞英文缩写 |
| `ko_kr` | 语序（动宾倒置）、敬语层级 | UI 文案用中性敬语；提示语避免命令形 |
| `ru_ru` / `de_de` | 词长显著长于英文 | 预留更宽的控件；见 §4.8 的溢出规则 |
| `fr_fr` / `es_es` / `pt_br` | 性数配合、形容词后置 | 带变量的句子必须整句翻译，不要拼接 |

**判定手法**：把 `en_gb` 与 `en_us` 逐键求值差；**所有键的值完全相同**就说明 `en_gb` 是复制品，不是维护过的文件。同理 `zh_tw` 与 `zh_cn` 逐键比对，只有字形差异（可用繁简转换双向验证）也说明没做用词校对。

### 4.7.1 文言（`lzh`）的具体口径

- 允许的句式：`不可`、`勿`、`欲…者`、`故`、`是以`、`皆`、`咸`。
- 禁止的写法：现代白话直译（`你不能这样做` → 应作 `不可如是`）、网络用语、语气词堆叠。
- 专有名词（模组名、物品名、生物名）保留原文或按既有译名，不意译。
- 数值与单位照抄，不做文言化改写（`3 秒` 不写成 `三息`）。
- 标点：用全角，句末可用 `。`；不使用现代感叹号堆叠。

### 4.7.2 繁体两地（`zh_tw` / `zh_hk`）的具体口径

| 词 | `zh_tw` | `zh_hk` |
|---|---|---|
| 软件 | 軟體 | 軟件 |
| 信息 | 資訊 | 資訊 / 訊息 |
| 默认 | 預設 | 預設 |
| 视频 | 影片 | 影片 |
| 网络 | 網路 | 網絡 |
| 打印 | 列印 | 打印 |

- 上表是**用词差异的示例**，不是完整词典；维护时按目标地区的通行译法逐条确认。
- 只做繁简转换而不校对用词，是最常见的"看起来做了、实际没做"。

## 4.8 文案与 UI 的溢出规则（多语言必然遇到的布局问题）

同一段文案在 `de_de` / `ru_ru` 里可能比 `en_us` 长 40% 以上。若布局按英文长度写死，换语言就会截断或溢出。

| 场景 | 规则 | 判定手法 |
|---|---|---|
| 按钮宽度 | 按**最长语言**实测，不用英文长度换算 | 切到 `de_de` / `ru_ru` 看按钮是否被截断 |
| tooltip 高度 | 按**折行实测**，不按字符数估算 | 把提示塞满长句，看是否溢出屏幕 |
| 单行文本控件 | 允许换行或允许滚动 | 换语言后检查是否有 `…` 截断 |
| 数字与单位 | 数字单独成组件，单位随语言 | 避免"3s"这类缩写进语言值 |
| 变量占位 | 整句翻译，`%s` 顺序由译者决定 | 用带参数的可翻译组件，不拼接 |

- **禁止用真实数值换算出的布局量补位**：`x = 字数 * 像素` 这类算法在换语言后必然错。要么实测，要么交给布局系统。
- **禁止在语言值里写换行符**：换行由布局决定；语言值里写 `\n` 在经 `expand` 的文件里还会变成真实换行破坏 JSON（见 [03-metadata.md](03-metadata.md) §3.3.5）。
- **GUI 文案的颜色由绘制函数给**，不写 `§`（见 §4.2.2）。

### 4.8.1 多语言回归的最小验证集

不必 13 种全验，但以下四种必须验，它们覆盖了绝大多数布局与文案问题：

| 语言 | 覆盖的问题 |
|---|---|
| `en_us` | 基准：键是否齐、布局基准是否正确 |
| `zh_cn` | CJK 字形宽度、中文换行、颜色丢失（第三方 UI） |
| `de_de` | 长词溢出、按钮截断 |
| `lzh` | 短句语义、文言是否被误写成白话 |

判定：四种语言下各触发一次主要交互（打开配置界面、触发一次提示、看一次 tooltip），确认无截断、无原始键、无色码丢失。

## 4.9 语言文件的维护流程（新增 / 修改键的固定顺序）

| 步骤 | 动作 | 判据 |
|---|---|---|
| ① | 在 `en_us` 里新增 / 修改键 | 键名符合 §4.5 约定；值单行、无 `§`、无转义 |
| ② | 同步到全部语言文件 | 每个文件都有该键（值可先为英文原文） |
| ③ | 逐语言求键集合差 | 与 `en_us` 对称差为 0 |
| ④ | 严格 JSON 校验 + BOM 检查 | 全部文件可解析、首三字节非 `EF BB BF` |
| ⑤ | 构建 | `BUILD SUCCESSFUL` |
| ⑥ | 解包回读产物里的语言文件 | 产物键集合与源一致 |
| ⑦ | 实机切换语言验证 | 中文客户端显示中文，无原始键 |

- **顺序不能颠倒**：先构建后补键，缺键会被打进产物；补完不重建，产物仍是旧的。
- **修改已有键的值**属于"文案变更"，跨版本线必须同步；只改一条线会造成同一模组在不同版本上说不同的话。
- **删除键**要谨慎：第三方翻译平台按 key 记录进度，删键会让该语言的进度记录失配。确需删除时，先在所有语言文件里一起删，再重建。

### 4.9.1 键集合差的具体判定

```bash
# 对称差（缺键 + 多键），输出为空即齐平
diff <(jq -r 'keys[]' assets/<mod_id>/lang/en_us.json | sort) \
     <(jq -r 'keys[]' assets/<mod_id>/lang/zh_cn.json | sort)
```

- **只多不缺**也不行：多出来的键在 `en_us` 里没有对应条目，说明该文件混入了废弃键，会让"键齐平"的判断失效。
- 嵌套 JSON 的语言文件要递归取叶子路径（`jq -r 'paths(scalars) | join(".")'`），只取顶层键会漏掉嵌套差异。

## 4.10 服务端 / 客户端语言不一致的排查

聊天提示、命令反馈这类文本由**服务端构建组件、客户端解析翻译**，因此存在"两端语言不同"的天然错配。

| 现象 | 根因 | 判定手法 | 修复 |
|---|---|---|---|
| 中文客户端看到英文 | 组件是 literal 写死的 | grep 玩家可见路径的 `literal` | 改可翻译组件（§4.3） |
| 中文客户端看到原始 key | 接收端没装模组 / 缺键 | 看提示文本是否形如 `message.xxx.yyy` | 用 `translatableWithFallback` 或补齐键 |
| 只有部分玩家看到 key | 该玩家客户端语言缺该键 | 比对玩家语言代码与该语言文件 | 补齐该语言键 |
| 服务端日志里是中文、玩家看到英文 | 日志用服务端语言，提示用客户端语言 | 分别检查日志与提示的构建位置 | 提示不要复用日志文案 |
| 换了语言但提示没变 | 组件在服务端构建后缓存 | 看是否有静态缓存的 Component | 每次发送时重建组件 |

- **判定要点**：先确认文本是"原始 key"还是"另一种语言"。前者是缺键 / 缺模组，后者是 literal。两种根因完全不同，修法也不同。
- **1.20.1 及更早没有客户端语言读取口**，兜底只能固定 `en_us`；这是该版本线的已知限制，不是 bug（见 §4.3.5）。

## 4.11 多来源语言文件的合并与优先级

模组语言不止来自自己那一份 `lang/*.json`：resource pack、服务端下发、其它模组都可能提供同键翻译。合并顺序错了，表现为"文件里明明写了，游戏里显示的是别的"。

| 来源 | 优先级（高 → 低） | 说明 |
|---|---|---|
| 玩家自定义resource pack | 最高 | 玩家主动覆盖，必须生效 |
| 服务端下发的resource pack | 次高 | 服务器统一文案；瘦客户端完全依赖它 |
| 本模组 jar 内的 `lang/*.json` | 中 | 基准来源 |
| 其它模组 / 前置提供的同键翻译 | 低 | 会被上面覆盖 |
| 兜底字符串（代码里） | 最低 | 仅在键完全缺失时使用 |

- **同键冲突的判定手法**：在 `zh_cn` 下显示的文字与 jar 内 `zh_cn.json` 的值不一致，说明有更高优先级的来源覆盖了它。逐个停用resource pack / 断开服务端下发，定位是哪一层。
- **服务端下发场景的固定排查顺序**：① 三端 jar 是否同版本 → ② 服务端是否重启过（换 jar 后必须重启才重扫）→ ③ 客户端是否重新进服拉过新resource pack → ④ 才看代码。前三步不确认就查代码，等于在错误的层面上找问题。
- **语言合并工具的兜底不能替代源文件合格**：部分框架会在加载时 strip BOM、合并缺失键。这类兜底能"让游戏跑起来"，但**带 BOM 的源文件、缺失的键仍判不合格**——兜底不是规范。

### 4.11.1 键缺失的三层兜底（按可靠性排序）

| 层 | 机制 | 可靠性 | 何时使用 |
|---|---|---|---|
| ① | 语言文件里键齐全 | 最高 | 默认要求 |
| ② | `translatableWithFallback(key, 兜底)` | 高（1.20.2+） | 跨端提示（接收端可能没装模组） |
| ③ | 框架层合并 / 补键 | 中 | 只作为运行期保护，不作为源文件豁免 |
| ④ | 显示原始 key | 最低（可接受降级） | 无兜底 API 时的唯一选择 |

- **不要依赖 ③ 来省掉 ①**：合并层能补的键是"别的模组恰好也提供了同一个键"，跨模组同键本来就是巧合，不能当设计。
- **④ 是明确允许的**：老版本线没有兜底 API 时，宁可让玩家看到 key，也不要用 literal 写死文案（见 §4.3.3）。

## 4.12 翻译交接与外部翻译的注意事项

把语言文件交给外部译者 / 翻译平台时，有几条约束必须提前说明，否则收回来的稿子会破坏键齐平。

| 约束 | 原因 | 交付时的写法 |
|---|---|---|
| **键名一个字符都不能改** | 改键等于新增了一个没人翻译的键，原键变缺键 | 只允许改值，不允许动键 |
| **不许增删键** | 多出来的键在 `en_us` 里没有对应条目 | 缺翻译就保留英文原文，不要删行 |
| **保持 JSON 结构与嵌套** | 扁平化后再还原会丢失层级 | 给原文件，不要给导出的表格 |
| **值必须是单行、无转义** | 经 `expand` 的文件里 `\n` 会变成真实换行破坏 JSON | 需要换行的文案由布局处理 |
| **不写 `§` 色码** | 第三方 UI 不解析，颜色静默丢失 | 颜色由代码给 |
| **保留变量占位符** | `%s` / `%d` 丢了会导致运行期格式化失败 | 占位符原样保留，顺序可按语言调整 |
| **编码 UTF-8 无 BOM** | 带 BOM 的源文件判不合格 | 明确要求，并在收回后校验首三字节 |

**收回后的验收动作**（缺一步都会把问题带进产物）：

1. 与 `en_us` 求键集合对称差，必须为空；
2. 严格 JSON 解析全部文件；
3. 首三字节检查，无 BOM；
4. grep 语言值里是否混入 `§` 与 `\n`；
5. 变量占位符数量与 `en_us` 对齐；
6. 构建后解包回读，确认产物里的语言文件与源一致；
7. 实机切换该语言，抽查 3 条主要文案。

### 4.12.1 变量占位符的对齐判定

```bash
# 逐键比对占位符数量（%s / %d / %1$s 等）
jq -r 'to_entries[] | "\(.key)\t\(.value|tostring|scan("%[0-9]*[$]?[sd]")|length)"' \
  assets/<mod_id>/lang/en_us.json > /tmp/en.txt
```

- 占位符**数量不一致**会导致运行期格式化抛异常或显示错位；**顺序不一致**在允许重排的语言里是正常的（用 `%1$s` 显式编号即可）。
- 判定口径：数量必须一致；若某语言需要调整顺序，必须全部改成显式编号形式，不能混用隐式与显式。

## 4.13 本地化自检清单（常驻）
