# 07 多版本移植策略

> 本文件管"一个模组怎么覆盖多条 MC 版本线"：判定层次、触点差分、探针手法、range 纪律、分支方案、老版本适配、执行波次。
> 上游：`SKILL.md`（结论以它为准）；本文件给判据、命令与可复用的编排模板，**不含实现代码**。
> 落地动作走 [03-metadata.md](03-metadata.md)（元数据）/ [06-build.md](06-build.md)（构建档位）/ [08-deploy-qa.md](08-deploy-qa.md)（验收）。
> 相邻模块：[05-mixin-api.md](05-mixin-api.md)（触点 A/B/C 的 API 细节）、[11-verdicts.md](11-verdicts.md)（易错结论对照）。

标签约定：**铁律** = 违反会导致构建失败、功能静默失效或已发布物返工；**约定** = 推荐做法，可按项目调整；**实测** = 有一手证据；**推断** = 未实测，**不许据此放宽版本声明或发布**。

## 7.1 先想清楚：什么在决定"要不要切分支"

一个 jar 能不能跨版本，只有三层在卡。逐层判，**别一上来就按 MC 版本号切**：

| 层 | 卡什么 | 典型轻量模组（纯指令拦截 + Mixin + 配置）的实测 |
|---|---|---|
| **L1 源码触点** | 真正调用的 MC / 加载器 API 的签名与包路径 | 往往只有 3 处会被打断（见 §7.2）。有些调用点**从 1.18.2 到 26.3 一次都没变过**，这类零变化的点不需要分支 |
| **L2 工具链硬边界** | Java 大版本、映射 / 混淆体系、模板结构 | Java **17** = 1.18~1.20.4；**21** = 1.20.5~1.21.11；**25** = 26.1~26.3。L2 与源码无关，**即使 L1 零差异也必须切** |
| **L3 加载器可用性** | 该 release 有没有对应加载器构建 | 见 §7.7 的空洞清单。L3 不决定"能不能并"，只决定"分发时能挂哪几个端" |

**判定规则（这套方法的唯一核心）**：

> **L1 决定"能不能并"，L2 决定"该不该分"，L3 决定"分发时能挂哪几个端"。**
> **合并只在 L1 有实测零差异证据时才做；`minecraft_version_range` 永远不得宽于已实测区间。**

三层各自需要什么证据：

| 层 | 需要什么证据 | 证据强度 |
|---|---|---|
| L1 | 分支间 `git diff -w` 源码零差异 **或** 触点 A/B/C 逐项同形态 | **实测** |
| L2 | 该 release 的 `javaVersion.majorVersion`、映射体系、模板结构 | **实测**（逐版本抓） |
| L3 | maven 元数据里该 release 的构建存在 | **实测** |

**三者缺一即分叉。** 缺证据时写"推断"标签，并在 range 里按已实测区间收窄。

## 7.2 找触点的方法：用差分反推耦合面

**不是通读源码，而是用分支之间的差分反推耦合面**：

1. 取全部历史分支，两两做差分：

   ```bash
   git diff -w <branchA> <branchB> -- common/src/main/java
   ```

   `-w` 是为了把 CRLF / 缩进噪声和真实 API 变更分开——**不加 `-w` 会看到满屏假差异**，结论直接失效。

2. 读差分结果：注意哪些分支**零差异**、哪些只差几行。零差异的分支是可以合并的候选；差几行的，那几行就是全部耦合面。

3. 把"变化的那几行"抽出来，就是触点清单。典型的三触点形态：

| 触点 | 内容 | 观测到的形态迁移 |
|---|---|---|
| **A** | `Commands#performCommand` 描述符 | 1.18.2 `(CommandSourceStack,String)I` → 1.19.2 / 1.20.1 `(ParseResults,String)I` + `remap=true` → 1.21.1 起同参数但 **`)V`** 且去掉 `remap` |
| **B** | OP 等级判定 | 1.21.1 `player.hasPermissions(2)` → **1.21.9 起** `player.permissions().hasPermission(Permissions.COMMANDS_GAMEMASTER)` |
| **C** | 聊天组件 | 1.18.2 用已删除的 `TranslatableComponent` → 1.19+ 用 `Component` |
| — | `ServerPlayer#setGameMode(...)Z` | 1.18.2 → 26.3 **全程无变更**（这类"零变化"的调用点不需要分支） |

**通用做法**：耦合面越少，跨版本越便宜。**先量出耦合面，再谈分支数**——顺序反了就会不自觉地"每个 MC 版本开一条分支"，维护成本按 release 数线性爆炸。

> ⚠ 权限触点 B 的真实时点曾被两次写错（先说 1.21.2、后说 26.1），**实测是 1.21.9**。教训：**形态边界必须两侧实证，不能按"系列感"推测**。两侧实证的方法见 §7.6。

### 7.2.1 触点清单的写法（每分支一行）

每条分支维护一行触点卡，字段固定：

| 字段 | 取值示例 |
|---|---|
| 分支 | `1.20.5-1.20.6` |
| MC / 端 / Java | 1.20.5–1.20.6 / Fabric+NeoForge / 21 |
| 构建档 | Loom 1.9-SNAPSHOT + MDG 2.0.49-beta + Gradle 8.11 |
| **触点 A 形态** | `(ParseResults,String)V` |
| **触点 B 形态** | `hasPermissions(2)` |
| **触点 C 形态** | `Component` |
| 基线来源 → 动作 | 从 `1.20.1` 移植 → 新建 |
| 验收实例 | （按 [08-deploy-qa.md](08-deploy-qa.md) §8.2 判定） |

图例：✅ 一手实测、⚠ 推断（必须探针，否则不许放宽）、✗ 该端不存在。**这张卡是 range 的唯一依据**，写不出卡上字段的 release 就不该出现在 `minecraft_version_range` 里。

## 7.3 一手资料来源（可复现）

二手转述（百科 / 论坛）只用来提假设，不用来做结论。

| 要查什么 | 一手来源 | 取哪个字段 |
|---|---|---|
| MC 发行清单、Java 要求 | `launchermeta.mojang.com/mc/game/version_manifest_v2.json` + 逐版本 version JSON | `javaVersion.majorVersion`（**逐版本抓**，不要假定"某 minor 都是同一 Java"） |
| NeoForge 可用区间 | `maven.neoforged.net/releases/net/neoforged/neoforge/maven-metadata.xml` | `<version>` 列表，前缀即 MC minor（`20.2.x`→1.20.2、`21.11.x`→1.21.11、`26.x`→26.x）。**另有一个必须同查的坐标** `.../net/neoforged/forge/maven-metadata.xml`——它是同一组织发布的 **MC 1.20.1 Forge 分叉**（该坐标只有 1.20.1，最新 `47.1.82`），漏查会得出"NeoForge 不支持 1.20.1"的错结论 |
| Forge 可用区间 | `maven.minecraftforge.net/net/minecraftforge/forge/maven-metadata.xml` | `<version>` 形如 `1.20-46.0.14`，取 `-` 前段 |
| Fabric API 覆盖 | `maven.fabricmc.net/net/fabricmc/fabric-api/fabric-api/maven-metadata.xml` | `<version>` 形如 `0.83.0+1.20`，**必须用锚定 `+1.20$` 精确匹配** |
| 代码形态 | 各分支 `git diff -w` | 见 §7.2 |
| 声明范围 | 各分支根 `gradle.properties` | `minecraft_version` / `minecraft_version_range` / `*_loader_version_range` |
| 实例真实加载器 | 实例 `<version>.json` 的库坐标 | 见 [08-deploy-qa.md](08-deploy-qa.md) §8.2 |

**踩坑提示（真实发生过的检索错误）**：查 Fabric API 是否支持 1.18.1 时，若用 `+1.18.1` 的**非锚定**子串匹配，会把 `+1.18.12`、`+1.18` 之类一并计入，从而"查到"根本不存在的构建。**正则不加 `$` 会造出幻觉数据。**

同类：查 NeoForge 时只看主 artifactId 就下"不存在"结论，也是检索口径错误（见上表第二行）。

## 7.4 range 的三类虚假承诺（通用规则）

`minecraft_version_range` 写错有三种方向，**危害与发现难度完全不同**，要分开治。

### 7.4.1 上界虚高

- 表现：`minecraft_version_range` 的上界写到了工具链 / 触点没覆盖的 release。
- 后果：用户装了崩，**比不装更糟**——崩溃会被记成"这个模组坏了"。
- 根因：把"看起来同系列"当成"实测过"。
- 判定手法：把上界拆成逐个 release，每个 release 对一遍 L2（Java 档）与触点 A/B/C 形态。任一不同即为上界虚高。
- 修复：上界对齐"下一个 L2 / L1 硬墙"，墙外的 release 一律不出现在 range 里。
- **唯一防线是 L2 / L3 实测，不是感觉。**

### 7.4.2 下界虚高

- 表现：range 下界比实际能跑的版本高（例如触点形态在更早的 release 就一致，却把下界写在后面）。
- 后果：**白丢用户，且只会以静默方式发生**——模组列表里直接不显示，没人来报 bug，所以最容易长期不被发现。
- 判定手法：对下界之前的每个 release 核一遍触点形态与 L3 可用性；全部一致即可前移。
- 修复：逐个 release 有 L1 证据才前移下界；**前移下界和改上界一样，都要重跑全部 6 处声明位**（见 §7.7.1）。
- 附加代价：下界前移可能撞上 L3 空洞（某 release 没有该端的加载器构建），这时只能"前移到空洞前一个 release"。

### 7.4.3 范围宽于证据

- 表现：range 覆盖了一段**从没实测过**的区间（编译能过、没实机装过）。
- 后果：写的时候顺手，出事的时候没人记得当初没测。
- 判定手法：把 range 里的每个 release 标 ✅ / ⚠ / ✗；出现 ⚠ 就是这一类。
- 修复：**下笔时把"测过哪些 release"当成 range 的唯一依据**；未实机的 release 不进 range，也不进发布平台的 `gameVersions`。

### 7.4.4 抽象示例

假设某模组有 4 条分支，声明如下（示例数据，用于对照三类病）：

| 分支 | 声明 | 诊断 | 依据 |
|---|---|---|---|
| 分支 α | `[1.18.2, 1.19)` | 诚实，但**下界偏高** | 更早两个 release 的触点形态与它完全一致，本可放宽；但其中一个 release 在 Fabric 端无独立构建（L3 空洞） |
| 分支 β | `[1.20.1, 1.22)` | **上界虚高（最严重）** | 上界跨过了两个硬墙：①某 release 起要求 Java 21，本分支工具链是 17；②触点 A 在某条线上变成 `)V`，mixin 目标直接失配；③某加载器下限在某 release 抬升。**同时上界虚高、下界却把更早的 release 关在门外** |
| 分支 γ | `[1.21.1, 1.22)` | **范围宽于证据** | 中间多个 release 一个都没实测过。上界方向合理但缺证据，须先跑 §7.6 探针再决定保留还是收窄 |
| 分支 δ | `[26.1.2, 26.2)` | **反向虚假承诺（低估自己）** | 更早的补丁版本与它触点零差异，却因下界写成具体补丁号而对那些版本报"不兼容"。**用户看到的"装不上"里有相当比例是 range 写窄造成的，不是真不兼容** |

三条结论：

1. **上界虚高**让用户崩溃，**下界虚高**悄悄丢用户，**范围宽于证据**最不负责任——三种都要治，但只有第一种会收到 bug 报告。
2. **同一族里源码零差异却各占一条分支 + 一段区间**，是纯粹的维护浪费：白白多维护一条线，且两条线的 range 迟早会漂。
3. **单点 range**（`[26.1.2]` 这种只有一个值的闭区间）是合法写法，用于"只承诺这一个 release"的场景；但要注意它同样会造成下界虚高。

### 7.4.5 同一病根的其他表现

- **文档缺席被当成事实否定**：据"官方文档查不到某字段"推断字段不存在。**文档未收录 ≠ 不存在**；以实机 / 反编译为准。
- **变更说明写成功能承诺**：见 [06-build.md](06-build.md) §6.4.1。
- **旧式 `§` 色码**：文本里带色码等于承诺"这里会是红色"，在第三方聊天 UI 下静默失效（见 [04-i18n.md](04-i18n.md)）。
- **工具给出的"成功"信号不可信**：`git push | tail` / 上传命令 `| grep | head` 的退出码是管道末端的，出现过"报告已完成且 exit 0、实际整条构建 FAILED"。**一律改为带外回读验证**（远端 `ls-remote` 哈希比对、上传后按 File ID 查回）。
- **"某 release 有 loader 构建 ⇒ 本模组的 jar 装得上"**——不等价。loader 有构建只解决"能不能装"，不解决"装了跑不跑"；只有实机验收能证明。**未实机的 release 在发布平台上就不填 `gameVersions`。**

## 7.5 分支方案的设计口径

### 7.5.1 分支切分的判断表

| 切分依据 | 该不该单独开分支 | 说明 |
|---|---|---|
| Java 档变化（17 → 21 → 25） | **必须** | L2 硬边界，与源码无关 |
| 触点 A/B/C 任一形态变化 | **必须** | L1 差异，混在一起只能靠 mixin 双写 |
| 加载器可用性出现空洞（某 release 无某端构建） | **不必** | 只影响该端的 range / 分发，不影响源码合并 |
| 模板结构演进（`buildSrc` → `build-logic`） | **视情况** | 若与插件档位冲突则必须拆 |
| 只是补丁号不同、源码零差异 | **不必** | 合并成一条区间分支，range 写成闭区间 |

### 7.5.2 区间分支的覆盖校验

切完分支后做一次**全阶梯展开**，确认每个 release 恰好落在一条分支、没有空洞也没有重叠：

| release | 落点分支 |
|---|---|
| 1.20 | 区间分支甲 |
| 1.20.1 | 区间分支甲 |
| 1.20.2 | 区间分支乙 |
| 1.20.3 | 区间分支乙 |
| 1.20.4 | 区间分支乙 |
| 1.20.5 | 区间分支丙 |
| 1.20.6 | 区间分支丙 |

⇒ **7 个 release，3 条分支。** 这张表是 range 的施工图：**每个 release 只能出现在一行**；出现两行是重叠（两条分支都会发布，用户会装到错的那条），一行都没有是空洞（用户搜不到）。

### 7.5.3 jar 总账

按"端 × 分支"统计产物数量，用来估上传与长期维护成本：

| 端 | 出现在哪些分支 | jar 数 |
|---|---|---|
| Fabric | 全部区间分支 | 每条分支 1 个 |
| Forge | 仅 Forge 有构建的分支 | 视 L3 |
| NeoForge | NeoForge 有构建的分支 | 视 L3 |
| **合计** | | **jar 数 × 端数 = 发布物料总量** |

**每多一个端，就多一条构建线 + 一份上传物料 + 一份长期维护成本。** 出不出某个端，按 §7.5.4 的决策表判。

### 7.5.4 可选增补：要不要给某分支多出一个端

| 情形 | 建议 | 理由 |
|---|---|---|
| 该端有官方构建 + 手上有对应测试用实例 | 出 | 能实机验收，声明才站得住 |
| 该端与已有端**源码同源**（同一坐标分叉） | 倾向不出 | 分发页要两份依赖声明，收益低；若出，元数据 groupId 不同，**必须实机验证** |
| 该端构建极少（个位数） | 谨慎 | 元数据形态可能落后于当前写法，回填后须实机验证，不能只靠编译通过 |
| 手上没有该 release 的测试用实例 | 不出或标注未实机 | 不出就只能"装了却没法测"；出了就必须诚实标注"未实机" |
| 该 release 某端**借相邻构建**（如借相邻版本的 API） | 借则必须实机验证 | **不许留着"支持 X"的声明却没人验证** |

## 7.6 落地前必须先跑的探针

边界是**推断**的时候，逐个 release 解析 dev 产物后核对 A / B / C。

### 7.6.1 探针命令

```bash
# 触点 A：Commands#performCommand 的存在性与描述符
javap -p -s path/to/net/minecraft/commands/Commands.class | grep -A2 performCommand

# 零变化点复核：setGameMode 是否真的没变
javap -p -s path/to/net/minecraft/server/level/ServerPlayer.class | grep -A1 "setGameMode"

# 触点 B：权限相关方法的存在性与签名
javap -p -s path/to/net/minecraft/server/level/ServerPlayer.class | grep -i "permission"
```

### 7.6.2 判定规则

| 探针结果 | 动作 |
|---|---|
| A / B / C 与相邻分支**全部一致** | 并入同一条分支、放宽 range |
| **任一不同** | 另开分支 |
| 某 release 的类**找不到**（`javap` 报错） | 包路径已变，按新路径重查；**不要假定"同一个类名"** |
| 描述符与相邻分支不同但方法名相同 | 属真实差异，必须另开分支（方法名相同最容易误判成"没变"） |

### 7.6.3 老版本换映射名重跑

1.16.5 用 `net/minecraft/command/ICommandSource` + `server/level/ServerPlayerEntity`；1.12.2 / 1.7.10 用 MCP 映射名（`CommandManager` / `CommandHandler` / `EntityPlayerMP`）。**同一套探针脚本换映射名即可复用**，不要另写一套。

### 7.6.4 需要下调置信度的信号

Fabric 官方按版本**联合发兼容公告**，而某些 release 是**单独发的**——说明官方把它们当破坏性版本。判据：看官方公告的发布时间与覆盖版本，单独发公告的 release 要单独探针，不能与相邻版本合并。

**分组先验（官方公告口径，仅作分组假设，不作结论）**：`1.19~1.19.2`、`1.20~1.20.1`、`1.20.3~1.20.4`、`1.20.5~1.20.6`、`1.21~1.21.1`、`1.21.2~1.21.3`、`1.21.6~1.21.8`、`1.21.9~1.21.10`；而 **1.21.4、1.21.5、1.21.11、26.1、26.2、26.3 是单独发公告的**。

⇒ 若某单独发公告的 release 动了 A / B / C，就把区间拆开（例：`1.21.2~1.21.3` + `1.21.4` + `1.21.5`）。

### 7.6.5 Fabric Loader 下限（L3 硬下限）

| MC 线 | Fabric Loader 下限 | Loom 下限 |
|---|---|---|
| 1.21.9 / 1.21.10 | `0.17.2` | — |
| 26.1 | `0.18.4` | 1.15 |
| 26.3 | `0.19.5` | 1.17 |

`depends.fabric-loader` 写低于下限的版本，用户侧会被加载器拒绝启动——**这是加载器硬校验，不是建议值**。

### 7.6.6 兜底 API 的引入版本也是探针项

多语言兜底（`Component.translatableWithFallback` 一类）的引入版本必须先探：**1.19.2 不存在**。这条直接决定"基线新增的多语言兜底能否回填到低版本分支"。

- 结论与降级策略见 [04-i18n.md](04-i18n.md) §4.3。
- 探针手法：对该 release 的 `Component` 类跑 `javap -p -s`，看有没有该静态工厂方法；**存在性判断不看文档，看字节码**。
- **未确认前禁止回填**——低版本分支会直接编译失败。

## 7.7 放宽 / 收窄 / 合并的操作口径

### 7.7.1 一条分支的"版本声明"由 6 处构成

改 range 不是只改一个数。漏改任何一处都会造成**能跑却装不上**或**装得上却崩**：

| 声明处 | 位置 | 放宽时的注意事项 |
|---|---|---|
| `minecraft_version` | `gradle.properties` | 编译目标，仍是**单个**版本。放宽靠 range，不靠改它 |
| `minecraft_version_range` | 同上 | 上界对齐"下一个 L2 / L1 硬墙"，**下界前移要逐个 release 有 L1 证据** |
| Fabric `depends.minecraft` | `fabric.mod.json` | 与 range 同义，但语法是 `~26.3` 这类**前缀约束**，跨 minor 必须改写 |
| Fabric `depends.fabric-loader` | 同上 | 有硬下限（见 §7.6.5） |
| Fabric `depends.fabric-api` | 同上 | 只要用到 API 类就是**真前置**，必须显式声明（`implementation` 不打包） |
| NeoForge / Forge 元数据 | `mods.toml` **或** `neoforge.mods.toml` + loader range | **改名时点在 1.20.6 前后**：≤1.20.4 用旧文件名 `mods.toml`，1.20.6+ 才见 `META-INF/neoforge.mods.toml`；Forge 侧 1.20 = 46.x / 1.20.1 = 47.x，一条分支覆盖两者时 loader range 要写成 `[46,)` |

**6 处齐改的检查手法**：改完 range 后，解包产物逐个读元数据（`unzip -p <jar> fabric.mod.json`、`unzip -p <jar> META-INF/mods.toml`），确认 6 处都是新值。**只改 `gradle.properties` 就发版，是"能跑却装不上"的典型来源。**

### 7.7.2 合并只在这三种证据下做

① 两分支 `git diff -w` 源码零差异；② 触点 A / B / C 全部同形态；③ L2（Java / 映射 / 模板结构）同档。

**三者缺一即分叉。** 合并后立刻做 §7.5.2 的阶梯展开校验，确认新 range 没有空洞。

### 7.7.3 loader range 的取值原则

取该分支覆盖区间的**下界线的 loader 起点**，不虚高。例：`1.20.2-1.20.4` → `[48,)`、`26.1-26.2` → `[62,)`、`26.3` → `[66,)`。

**Forge 版本 ↔ MC 线对照（一手 maven 版本表，注意 26.1 线是逐补丁号递增的，取错就会 404）**：

| MC 线 | Forge 版本段 | MC 线 | Forge 版本段 |
|---|---|---|---|
| 1.20.2 | 48.x | 1.21.6 | 56.x |
| 1.20.3–1.20.4 | 49.x | 1.21.7 | 57.x |
| 1.20.6 | 50.x | 1.21.8 | 58.x |
| 1.21.3 | 53.x | 1.21.9 | 59.x |
| 1.21.4 | 54.x | 1.21.10 | 60.x |
| 1.21.5 | 55.x | 1.21.11 | 61.x |
| 26.1 | 62.x | 26.1.1 | 63.x |
| 26.1.2 | 64.x | 26.2 | 65.x |
| 26.3 | 66.x | — | — |

### 7.7.4 L3 造成的分发空洞（要提前告知，否则会被误当成"模组有问题"）

| 空洞类型 | 具体 release | 应对 |
|---|---|---|
| **NeoForge 线上只有 beta 的 release** | 1.20.3（7 个构建全 beta）、1.20.5（22 全 beta）、1.21.2（2 全 beta）、1.21.6、1.21.7、1.21.9、26.3（7 全 beta） | 发布时 `releaseType` 如实标 beta，不伪装 release |

| **NeoForge 主坐标不存在 1.20.1 线** | 主坐标首个产物是 `20.2.3-beta` | 1.18~1.20.1 的 NeoForge 端只能走 Forge；但同一组织的 `net.neoforged:forge` 坐标发过 1.20.1 的 Forge 分叉（该坐标**只有 1.20.1**，最新 `47.1.82`）⇒ 1.20.1 **可以**额外出一个 NeoForge jar，需实机验证 |
| **Forge 构建数极少** | 1.20（7 个）、1.20.3（2 个） | 覆盖这些 release 的 Forge 端**元数据形态可能落后于当前写法**，回填后须实机验证，不能只靠编译通过 |

## 7.8 错误台账（防止被复述成事实）

| 现象 | 错误结论 | 纠正 |
|---|---|---|
| 拿分支名当 MC 版本号读 | 据某分支的 `minecraft_version` 与分支名不符，断言它"名不副实、建议改名归档" | **错在读不懂命名意图。**分支名承载的是作者语义（例如"旧代码形态存档"），与 MC 版本号无关。**观测到的事实是对的，由它推出的标签结论是错的。**教训：**不接受外部重新命名** |
| 双版本号 jar 产物 | — | 跑的是**改动前的构建**。修 `build-logic` 后必须重跑，别信旧产物 |
| `fabric.mod.json` 输出非法 JSON（`description` 里出现真换行） | 一度怀疑 `expand` 的转义处理有 bug | 根因是 `expand` 走 Groovy `SimpleTemplateEngine`，模板体被编译成双引号 GString ⇒ **源文件里的 `\n` 会先变成真换行**。`jsonExpandProps` 只保护被替换的值，不保护正文。**凡经 `expand` 的 JSON，正文一律禁写转义** |
| "NeoForge 起点 1.20.2，所以 1.20.1 出不了 NeoForge 端" | 依据主坐标首个产物 `20.2.3-beta` 下断言 | **查了错的坐标。**该组织另有 `net.neoforged:forge`，专发 MC 1.20.1 的 Forge 分叉（最新 `47.1.82`）。教训：**"某加载器不存在于版本 X"必须由全部相关坐标反证，不能只看主 artifactId** |
| "文档写的 Java 8 路径能构建老版本 / 全盘只有一个 JDK 带 javac" | 只扫了一处 JDK 目录，就把结论放大成"全盘" | **两句都错，实测推翻。**①扫描范围漏了 Gradle 自动下载的 JDK 与启动器自带的 runtime（后者**带 `javac 21.0.7`**，嵌套 5 层深）；②原文那行本来就写"**运行** / 兼容旧环境"，是把"运行"读成"构建"再回头怪文档——**降级表的列语义要先读清楚**。定位 JDK 的方法见 [02-environment.md](02-environment.md) |
| "缺 Java 8 ⇒ 老版本一定建不了" | 把"缺 JDK 8"当成绝对阻塞 | 收窄后才是真问题：实测 `--release 8` 在 17 / 21 / 25 三档全部成功，产物 major 均 52 ⇒ **目标字节码根本不是瓶颈**。真缺口只有两个：①某些安装包只是 JRE；②老 ForgeGradle 绑的老 Gradle 跑不动在新 JVM 上 |
| "foojay 目录名的 major 字段 8 与 18 会撞名，自动探测不可靠" | 凭目录命名格式推测 | **推测，未验证，撤回。**现有命名里 major 是 `-` 分隔的独立段，`8` 与 `18` 是两个不同字符串，正常解析不会撞。保留的稳妥做法只有一条：**老版本显式声明 vendor，别依赖自动探测** |
| `git push` 无限挂起 | 以为是网络 / 代理问题 | GCM 在无 TTY 时等交互输入静默挂死。见 [09-git-upload.md](09-git-upload.md) §9.4 |
| 两次"任务已完成 exit 0"实为 FAILED | 差点据此下令发布 | 管道退出码不可信 |
| 权限重构时点 | 先说"1.21.2 起"，后说"26.1" | **实测是 1.21.9**（`ServerPlayer#hasPermissions(int)` 在 1.21.9 已移除） |

## 7.9 老版本线：1.7.10 / 1.12.2 / 1.16.5 的独立单版本适配

这三条**各只适配列出的那一个 release**，不出 Fabric / NeoForge 端，不扩其他小版本，但**留好钩子**。

| MC | Forge（一手 maven 实测） | Java | jar 数 |
|---|---|---|---|
| 1.7.10 | 163 个构建，最新 `1.7.10-10.13.4.1614-1.7.10` | 8 | 1 |
| 1.12.2 | 355 个构建，最新 `1.12.2-14.23.5.2864` | 8 | 1 |
| 1.16.5 | 136 个构建，最新 `1.16.5-36.2.42` | 8（11 亦可） | 1 |

**为什么不能并进现代线的区间分支**：L1 三触点在 1.18 之前是**另一套类体系**（`EntityPlayerMP` 而非 `ServerPlayer`、`CommandManager` / `CommandHandler` 而非 `Commands`、连 `TranslatableComponent` 都没有），差异不是"改个 range"级别。硬并只会让 1.18+ 的分支背上死代码。

### 7.9.1 老三条的触点（待探针确认）

- A′（1.7.10 / 1.12.2）：旧体系 `CommandManager` / `CommandHandler`。
- A″（1.16.5）：官方映射已有 `Commands`，但 source 类型是 `CommandSource` 而非 `CommandSourceStack` ⇒ **需 `javap` 定描述符**。
- B′：`EntityPlayerMP` 权限等级旧写法；1.16.5 旧名 `hasPermissionLevel(int)`（待实测）。
- C′：1.7.10 无 `Component`，用旧 `ComponentText` / `ComponentTranslation`；1.12.2 用 `TextComponentTranslation` 等；1.16.5 用 `TranslationTextComponent` / `ITextComponent`。

**构建环境状态**：结论是"目标字节码不是瓶颈，缺的是能跑老 Gradle 的 JVM"；先试 `--release 8` 路线，拿 1.16.5 当试验品。详见 [02-environment.md](02-environment.md)。

### 7.9.2 钩子怎么留（只留形状，不写实现）

- 三条分支各自根 `gradle.properties` 把 `minecraft_version` / `minecraft_version_range` / `java_version` / `forge_version` 四项**提为唯一改动点**，元数据与 `depends` 全部从这几个变量展开 ⇒ 将来要扩相邻补丁版本，只动 range、不换工程结构。
- `range` 先写**单点**（`[1.16.5]` 这种闭区间单值），扩版本时改区间即可，不需要重新判断"当初承诺过什么"。
- 语言文件、配置读写、提示文案这类**与 MC 无关**的部分保持与其它分支同名键，回填脚本才能一条命令扫全家族。
- 注入点未定：老版本大概率**不需要 Mixin**（Forge 早期自带命令事件），但属未实测；落地前先按 §7.6 的手法核一遍，再决定是 Mixin 还是事件。
- **配置与文案对齐**：配置字段名与语义与主线完全对齐，老三条不新增字段；触点差异全部收敛到**一个平台适配类**（如 `CommandHookBridge`），业务判定写在 common，老版本只实现桥。

## 7.10 执行编排：波次、决策点、逐分支卡

**边界**：把某个基线版本铺到全系列，并规定每条分支的构建档位、触点落点、元数据字段、验收路径、上传物料。**不管**：新功能、配置界面入口、语义变更。移植期间**只允许**因 API 形态被迫产生的差异；需要改行为的，停下来问，不在移植里夹带。

**顺序铁律**：**先探针后改码，先构建后部署，先本地验收后上传。**

### 7.10.1 要人点头的决策点（类型化，换项目同样适用）

| 决策类型 | 选项 | 判断要点 |
|---|---|---|
| 中间的 release 区间要不要出**多一个加载器端** | 出 / 不出 | 该端有无官方构建 + 手上有无对应测试用实例；不出就只能"装了却没法测" |
| 老版本构建路线 | 补 JDK / 用现代 Gradle + `release = 8` / 原地覆盖 | 先花半天实测成功率最高的那条；**先探后装** |
| 某分支要不要额外出**同源分叉 jar** | 出 / 不出 | 与主端源码同源、分发要两份依赖声明，收益低则不出 |
| 某 release 的某端**借相邻构建** | 借 / 放弃该端 | 借用必须在实机验证过才算数；**不许留着"支持 X"的声明却没人验证** |

### 7.10.2 波次与退出条件

| 波 | 内容 | 退出条件（不满足不许进下一波） |
|---|---|---|
| **W0 探针周** | 跑 A / B / C 探针（未采样 release + 兜底 API 引入版本）+ 构建档位实测 | 每个 release 的 A / B / C 有 `javap` 记录；可疑区间的**拆分与否**定稿；全部决策点有结论 |
| **W1 老版本线** | 顺序按成功率从高到低（1.16.5 → 1.12.2 → 1.7.10） | 三条各自：`build` 出 jar → 装进对应实例 → 服务端 / 局域网下行为与基线一致 → 无 `NoClassDefFoundError` |
| **W2 最老的现代分支** | 现分支**下界放宽**，6 处声明位齐改 | 已有实例实机通过；新增覆盖的 release 至少各一次实机或通过（未通过就收窄并回写声明） |
| **W3 相邻两条** | 一条放宽、一条**收窄 + 下界前移** | 新旧下界各实机一次（Forge 老 release 构建少、元数据形态可能落后） |
| **W4 新建区间（Java 跨界）** | 新建分支；Java 档跨界处 | 该区间每个 release 至少一次装载成功；A / B / C 与所属分支一致 |
| **W5 中段区间** | 上界收窄 + 下界前移；按 W0 结果决定是否再拆 | 有实例的先验；**无实例的只能编译验证，声明范围必须诚实标注未实机** |
| **W6 合并 + 全系列回填** | 零差异分支合并；把基线的规范化增量（多语言兜底、图标字段分界、本地化补充）回填各分支 | 兜底 API 引入版本已确认；未确认前**禁止**回填（老分支会直接编译失败） |

**每波结束统一做**：`jar` 产物 MD5 记录 → 部署 → 实机验收 → 才允许该波分支推远端。

### 7.10.3 逐分支执行卡

字段模板见 §7.2.1。**每条分支一行、字段不许留空**；留空的那一格就是"未采样"，对应的 release 不许进 range。

### 7.10.4 上传准备（先备好，不执行）

每分支一份 `gradle.properties` 与自身 range；发布平台每分支备齐 changelog、`releaseType`（按"只有 beta 的 release"如实标）、`gameVersions`（**只填实机通过过的**）、dependencies、environment。上传脚本每分支只改版本号与文件路径两行。详见 [09-git-upload.md](09-git-upload.md)。

**发布时的版本串口径（与 range 同步）**：`gameVersions` 按**分支设计区间全列**（如 `1.21.9-1.21.11` → 填 `1.21.9` / `1.21.10` / `1.21.11` 三项）——既不写 `1.21.9-1.21.11` 这种范围字符串，也不只勾一版。range 放宽了但发布页仍只勾一个版本，用户照样搜不到。

## 7.11 推进顺序（不写代码，先钉事实）

1. **探针**：未采样区间的 A / B / C + 兜底 API 引入版本。跑完才允许动 range。
2. **零风险动作先行**：源码零差异的分支合并、只改声明不改代码的 range 修正。
3. **新建分支**：按 §7.7.1 的 6 处口径逐项落。
4. **回填基线增量**：元数据规范化 / 图标槽位 / 多语言。每批先过兜底 API 探针。
5. **发布侧对齐**：发布平台的 `gameVersions` 必须跟着 range 一起改，否则 range 放宽了、页面仍只勾一个版本，用户照样搜不到。

### 7.11.1 高版本线的 Forge 落地口径

- **插件**：≤1.21.8 用 FG6（`[6.0.24,6.2)`，绑 Gradle 8.x）；1.21.11 起用 FG7（`[7.0.3,8)`；26.x 用 `[7.0.17,8)`），官方 MDK 的 wrapper 是 Gradle 9.5 / 9.7。依据与 DSL 见 [06-build.md](06-build.md) §6.2。
- **Mixin 版本 ↔ 兼容级**：Forge ≤1.20.6 自带 Mixin **0.8.5**（只认 `JAVA_17`，且不能解析 major 65）；Forge ≥1.21.1 自带 **0.8.7**（认 `JAVA_21`）。⇒ 1.20.x 的 forge 产物必须 Java 17 字节码 + `JAVA_17`；1.21.5 / 1.21.8 保持 21 / `JAVA_21`；**26.x 是 25 源码 + `JAVA_21` 产物（major 需降到 65）**。详见 [05-mixin-api.md](05-mixin-api.md) §5.1.5。
- **独立工程**：当主工程 Gradle 大版本与 Forge 端所需冲突时，forge 端拆成独立 Gradle 工程（自带 wrapper），主工程 `settings.gradle` 注释掉 `include('forge')`；仍以分支 `gradle.properties` 为版本唯一来源。做法与坑见 [06-build.md](06-build.md) §6.2.4。
- **判据**：看 `forge/settings.gradle` 在不在——在 ⇒ 独立工程（用 forge 自己的 wrapper，任务 `jar`）；不在 ⇒ 子模块（用分支根的 wrapper，任务 `:forge:jar`）。写错报 `Task 'jar' not found in root project ...`。
- ⇒ **同一条 MC 线上，Forge 与 Fabric/NeoForge 可以各用各的 Gradle 档**，不必为"统一"去降级或硬并。

### 7.11.2 一句话总则

> **能并则并，但"并"必须有源码零差异 + 同 Java 档 + 加载器都可用这三份证据；range 的下界和上界同样危险——上界虚高让用户崩溃，下界虚高悄悄丢用户，而"顺手写的宽范围"是三者里最不负责任的一种。**

---

## 7.12 已作废：单工作树下的"更新某一版 → 再次构建"流程

**状态**：曾采用，现已改为"每个版本一个独立目录"，本流程当前不采用。

- 原适用场景：只有一个工作目录，靠 `git checkout <分支>` 在不同 MC 版本之间切换。
- **为什么不采用**：多条 MC 线共用同一份 `build/` 与 `.gradle/`，Gradle 的增量缓存（尤其 Loom 的 remap、MDG 的 `createMinecraftArtifacts`）有跨版本串味风险；每版本独立目录天然隔离。
- 其中两条教训仍然有效：
  1. **切分支前必须先提交或 stash**，否则未提交改动会被原样带到新分支（实测出现过一次把前一支的多个文件改动整份带过去）。
  2. **`build/`、`.gradle/` 被 `.gitignore` 忽略，切分支不会清**，跨 MC 版本重建前必须 clean。
- **当前口径**：每版本一个独立目录，目录名 = 分支名 = jar 区间标签；产物校验与部署走 [08-deploy-qa.md](08-deploy-qa.md)。
