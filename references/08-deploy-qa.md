# 08 测试部署与验收

> 本文件管"产物怎么进实例、进哪个实例、怎么确认真的进去了、怎么算验收通过"。
> 本文件与 `references/` 其余模块同属一个技能包，**没有上位总纲**；结论冲突时以一手证据为准。本文件给判定方法、命令与验收清单。
> 相邻模块：[06-build.md](06-build.md)（产物怎么出来）、[07-porting.md](07-porting.md)（每个分支该验哪些 release）、[09-git-upload.md](09-git-upload.md)（验收通过之后才谈上传）。

标签约定：**铁律** = 违反会导致构建失败、功能静默失效或已发布物返工；**约定** = 推荐做法，可按项目调整；**实测** = 有一手证据；**推断** = 未实测，不许据此发布。

## 8.1 部署三条规则

### 8.1.1 产物位置与"找不到就报告"

构建跑完（例如 `gradlew :fabric:jar :neoforge:jar`），产物在 `<module>/build/libs/`。部署时按游戏 / 加载器版本选目标实例；**没有相应测试用实例时报告，不要猜目标**。

判定手法：

```bash
# 1) 确认产物真的出来了，且 mtime 是本次构建
ls -l --time-style=full-iso <module>/build/libs/*.jar

# 2) 确认实例侧现状（有哪些同名 / 同 modId 的 jar）
ls -l <实例>/mods/ | grep -i "<modid>"
```

`build/libs` 里出现多个 jar 是正常的（历史产物 + 本次产物）。**不要靠"最新的那个"猜**——按文件名里的版本号 + mtime 双重确认。

### 8.1.2 自动拷贝的提问规则

- **仅第一次构建前**向用户提问并拿到明确指示（放到哪个实例 / 双端怎么分）。
- 确认后**后续构建直接自动拷贝到该已确认实例，不再每次询问**。
- 用户中途改目标实例时再提问；改完把新目标写进项目记录。

**为什么只问一次**：每轮都问会打断流程；一次都不问会装错实例。一次确认 + 变更时再问是成本最低的口径。

### 8.1.3 旧版本 jar 的处置（两个方向相反，别记反）

| 位置 | 处置 | 原因 |
|---|---|---|
| `build/libs` 内的旧版本 jar | **永不删除、永不移动、永不备份、永不记录**，留原位 | 它是构建历史，删了就没有回滚参照；"记录"只会制造一份过期台账 |
| 实例 `mods/` 内的旧版本 jar | **必须删除**，每次部署只保留每个 modId 最新一版 | 同 modId 双版本并存会被 FML 拒载（启动直接失败） |

- 部署台账**只记"部署了哪个新版本"**，不记"删掉了什么"。
- 判定手法：部署前 `ls <实例>/mods/`，把同 modId 的 jar 全部列出；部署后确认只剩一个，且版本号等于本次构建。

## 8.2 测试用实例的判定标准

### 8.2.1 命名前缀，不是"包含测试"

- **只有带特定前缀的目录才是测试用实例**（前缀由项目约定，例如 `测试用-`）。前缀是**字符串开头**，不是"名字里含这两个字"。
- ⚠ **名字里带"测试"的目录不一定是测试用实例**：整合包作者也常给实例起名带"测试"。判据是**前缀**，不是子串。
- ⚠ **目录名大小写不统一**（同一个作者会写出 `…Neo` / `…Neoforge` / `…forge` / `…Forge` 混用），**不要靠字符串匹配猜加载器**。

### 8.2.2 加载器判定：用库坐标，不用关键词（铁律）

**不要 grep `"fabric"`**。NeoForge 的 `<version>.json` 里含 `net.fabricmc:sponge-mixin`（NeoForge 自带 Fabric Mixin），按关键词 grep 会把 NeoForge 实例误判成 Fabric。

正确做法是按**库依赖坐标**判定：

| 命中 | 判定 |
|---|---|
| `net.neoforged.fancymodloader` / `net.neoforged:*` | **NeoForge** |
| `net.fabricmc.loader` / `net.fabricmc:*`（**排除 `sponge-mixin`**） | **Fabric** |
| `net.minecraftforge:*` / `cpw.mods.modlauncher` | **Forge** |

**判定口诀**：`net.neoforged.fancymodloader` ⇒ NeoForge；`net.fabricmc:fabric-loader` ⇒ Fabric；`net.minecraftforge:fmlloader` / `cpw.mods.modlauncher` ⇒ Forge。**NeoForge 也会带 `net.fabricmc:sponge-mixin`，所以"看见 fabric 字样"绝不能判成 Fabric。**

判定命令：

```bash
# 实例版本目录下的 <version>.json 里有 libraries 数组
python -c "
import json,sys
d=json.load(open(sys.argv[1],encoding='utf-8'))
for lib in d.get('libraries',[]):
    print(lib.get('name',''))
" <实例>/versions/<version>/<version>.json | sort
```

看输出里有没有 `net.neoforged.fancymodloader:loader` / `net.fabricmc:fabric-loader` / `net.minecraftforge:fmlloader` 三类坐标之一。**三类都不出现 ⇒ 该实例不是模组加载器环境**（原版 / 只有资源加载），不能作为验收目标。

### 8.2.3 版本号也从 JSON 取，不从目录名取

目录名里的版本号经常是作者手写的（`26.2` / `26.2.0` / `1.21.1` 混排），甚至与实际不符。**以 `<version>.json` 里的 `id` / `inheritsFrom` 为准**。

判定手法：`jq -r '.id' <实例>/versions/<version>/<version>.json`；有 `inheritsFrom` 时同时看父版本。

### 8.2.4 实例清单是快照，会过期

**任何写死的实例清单都会随装 / 删实例而过期。** 不要维护"实例台账表"，维护**枚举与判定的方法**：

**重扫触发条件**：① 装 / 删过游戏实例；② 升级了新 MC 版本；③ 记录里的目标实例路径不存在。

**枚举流程**：

1. 列出启动器的版本目录（`versions/` 或等价目录）下的全部子目录名。
2. 按 §8.2.1 的**前缀**筛出测试用实例候选。
3. 对每个候选读 `<version>.json`，按 §8.2.2 的库坐标判定加载器，按 §8.2.3 取真实版本号。
4. 结果按"MC 版本 × 加载器"排成矩阵，标出**哪些组合缺实例**。
5. 缺的组合就是"能构建但没法验收"的缺口，写进报告，**不要用相邻实例顶替**。

**抽象示例（枚举结果长什么样，数据是虚构的）**：

| 实例目录（前缀已抽象） | MC | 加载器 | 判定依据 |
|---|---|---|---|
| `测试用-1.20.1-Forge` | 1.20.1 | Forge | `net.minecraftforge:fmlloader` |
| `测试用-1.20.1-Fabric` | 1.20.1 | Fabric | `net.fabricmc:fabric-loader` |
| `测试用-1.20.1-Neo` | 1.20.1 | NeoForge | `net.neoforged.fancymodloader`（同时带 `sponge-mixin`，**不是 Fabric**） |
| `测试用-26.3-Fabric` | 26.3 | Fabric | `net.fabricmc:fabric-loader` |
| `测试用-26.3-Neoforge` | 26.3 | NeoForge | `net.neoforged.fancymodloader` |
| `测试用-26.3-Forge` | 26.3 | Forge | `net.minecraftforge:fmlloader` |

**矩阵的用途**：`MC × 加载器` 的每个格子要么有实例、要么明确标"缺"。**没有实例的格子，其产物只能编译验证，不能声称"已验收"。**

### 8.2.5 找不到目标实例时的处置（铁律）

**停下来报告。** 禁止：

- 靠目录名猜（`…Neo` 不代表一定是 NeoForge，见 §8.2.2）；
- 放进非测试用实例（整合包 / 正式游玩实例）；
- 放进标了禁部署标记的实例；
- 用"相邻版本实例"顶替（1.20.1 的 jar 放进 1.20.4 实例，即使能启动也不算验收）。

## 8.3 禁碰实例与部署纪律

### 8.3.1 哪些实例一律禁碰禁写

| 类型 | 识别方式 | 为什么禁 |
|---|---|---|
| 整合包实例 | 目录名 / 元数据指向某个整合包项目 | mods 里有几十到几百个模组，误操作代价极高（见过 285 个模组的实例） |
| 正式游玩实例 | 用户日常在玩的实例 | 装错版本会直接毁掉存档体验 |
| 带禁部署标记的实例 | 目录名里含约定的禁部署标记 | 明确声明了不许写入 |
| 名字像测试但**没有前缀**的实例 | 按 §8.2.1 判定 | 前缀才是判据 |

**识别手法**：先看前缀（是不是测试用实例），再看目录名有没有禁部署标记，最后读 `<version>.json` 确认加载器。**三步全过才允许写入。**

### 8.3.2 部署纪律（铁律）

1. **部署成功并记录 MD5 之前不得结束输出**——不许"我拷过去了"就收工。
2. **目标实例游戏进程运行中时中止部署并等用户关闭后继续**，不得半途收工。
3. 部署前后各出一份清单（文件名 + MD5），作为"装了什么"的唯一凭据。
4. **不要凭"我记得装了"下结论**；也不要凭"文件在"下结论——要凭 MD5 一致。

**为什么 MD5 是必需项**：拷贝可能被占用 / 部分写入 / 覆盖失败而不报错。只有比对哈希才能证明"实例里跑的就是刚构建的那个 jar"。

## 8.4 目标实例确认与部署流程

### 8.4.1 目标实例写在项目记录里

每个项目的目标实例**写在项目记录里**（示例：某项目 26.2 → `测试用-26.2-fabric` / `测试用-26.2-Neo`；26.3 → `测试用-26.3-Fabric` / `测试用-26.3-Neoforge`）。**部署时不重新推断，按记录执行**；记录与实况不符时停下报告。

### 8.4.2 部署前核对三件事

| 检查项 | 通过条件 | 不通过的后果 |
|---|---|---|
| **加载器一致** | 目录名后缀（`…Neo` / `…Neoforge` ↔ `-neoforge-`，`…fabric` ↔ `-fabric-`）与 jar 名一致，且与 §8.2.2 的库坐标判定一致 | 装进错加载器的实例，启动报"不支持的加载器"或直接不加载 |
| **MC 版本一致** | jar 支持的 MC 版本落在实例的真实版本号内（§8.2.3） | 启动崩 / 静默不加载 |
| **前置库齐备** | 实例里已有 jar 声明的前置，且版本落在 `depends` 区间内 | 加载器直接拒绝启动（**不是"友好提示"**） |

**第三项最常被漏**：前置缺失的表现是加载器拒绝启动，报错信息往往指向"缺依赖 modId"，而不是"前置没装"。

### 8.4.3 部署流程（六步）

1. **仅首次构建前**问用户确认目标实例（用户中途换目标时再问）；已确认实例在后续构建中直接自动部署，不再每次询问。
2. **报告清单**：放什么文件、放到哪个 `mods/`、同名旧文件如何处理。
3. **删除实例 `mods/` 内被替换的旧版本 jar**（仅保留该 modId 最新一版）；`build/libs` 旧 jar 仍留原位不删。
4. **部署后用 `Get-FileHash -Algorithm MD5` 比对**实例里的 jar 与 `build/libs` 产物，确认一致。
5. **把"已部署到 X，待实机验收"写进项目记录**（只记结论，不建"修复记录"目录）。
6. **部署前确认无游戏进程运行**；游戏运行中则等待（见 §8.3.2）。

### 8.4.4 MD5 回读（PowerShell）

```powershell
# 1) 本次构建产物
Get-FileHash -Algorithm MD5 "<build/libs 下的产物>" | Format-List

# 2) 实例里的落地文件
Get-FileHash -Algorithm MD5 "<实例>/mods/<同名文件>" | Format-List

# 3) 部署前确认无游戏进程
Get-Process | Where-Object { $_.ProcessName -match 'java|minecraft' } | Select-Object ProcessName, Id
```

判定：两个哈希**逐字符相同**才算部署成功。不同则重新拷贝并重算，**不许"看起来大小一样"就放过**。

**bash 等价写法**（无 PowerShell 时）：

```bash
md5sum "<build/libs 下的产物>" "<实例>/mods/<同名文件>"
```

### 8.4.5 从包内回读（部署三查的第三查）

版本号取自 `gradle.properties`（**禁止硬编码**）、产物 mtime 必须是本次构建、**从包内回读确认改动真在里面**——三查缺一不可。

```bash
# 回读元数据里的版本号
unzip -p <jar> fabric.mod.json | grep -i version
unzip -p <jar> META-INF/mods.toml | grep -i version
unzip -p <jar> META-INF/neoforge.mods.toml | grep -i version

# 回读 jar manifest（1.20.1 的 MixinConfigs 也在这里）
unzip -p <jar> META-INF/MANIFEST.MF
```

回读要确认：版本号与 `gradle.properties` 一致；改动的类 / 资源文件确实在包里（`unzip -l <jar> | grep <路径>`）；没有混进不该打包的第三方类。

## 8.5 验收清单（每个 jar 都要过）

### 8.5.1 逐项清单

| # | 检查项 | 判定标准 |
|---|---|---|
| 1 | 模组列表出现本模组 | **小图标在左侧**、版本号正确、License 显示正确；主页 / 反馈两个按钮可点 |
| 2 | 进服 / 局域网行为 | 与基线语义一致（拦截 / 放行都对）；聊天提示文案在对应语言下正确 |
| 3 | 权限侧 | OP（等级 2 / `COMMANDS_GAMEMASTER`）不受限 |
| 4 | 与常见 UI / 地图 / 配方类模组共存 | 启动不崩；**这些模组自己的客户端指令与按键不被误拦** |
| 5 | 卸载后无残留 | 卸掉本模组后其余模组仍能进世界（证明没留残留状态） |
| 6 | 资源类改动 | 能正常进入世界，**无"数据包错误"弹窗** |
| 7 | 配置文件 | 改动能热重载（若模组支持） |
| 8 | 前置声明 | 故意不装前置时，加载器给出明确拒绝（而不是运行期晦涩错误） |

### 8.5.2 为什么"混装"才算真验收

**空实例只验"能装"，混装才验"能打"。**

指令拦截类模组的唯一耦合点是服务端 `Commands#performCommand`，**不注册配方、不注册方块 / 物品、不注入 GUI**，因此与地图 / 配方 / tooltip / UI 替换类模组之间**没有代码级联动**。它们在这里的作用是**冲突与共存验证**：

- 验收要求逐条确认"这些模组自己的聊天栏 / 客户端指令没被误拦"（地图模组的路径点指令、tooltip 模组的隐藏键、模组菜单的客户端指令页）。
- 因为**误拦是本模组唯一可能的破坏形态**——它不注册内容，能造成的破坏只有"把别人的指令吃掉"。
- 判定手法：在混装环境里逐条触发这些模组的客户端指令，看是否被本模组的钩子吞掉；被吞就是**误拦**，属必修 bug，不是"兼容性问题"。

**共存测试的取样原则**（不写死清单，按能力取样）：

| 取样类型 | 取什么 | 验什么 |
|---|---|---|
| UI 整体替换类 | 会大范围注入 GUI 渲染的模组 | 最容易与客户端 mixin 冲突 |
| tooltip / HUD 类 | 会在 GUI 层叠加绘制的模组 | 验 GUI 层不冲突、不 NPE |
| 地图 / 客户端指令密集类 | 客户端注册多条指令的模组 | 验客户端指令不被服务端钩子误拦 |
| 配方浏览类 | 注册大量配方分类的模组 | 验无配方模组不受影响 |
| 配置 GUI 类 | 有自己的配置界面的模组 | 验配置入口不被抢 / 不崩 |
| 文案 / 本地化类 | 覆盖 lang 键的模组 | 验 lang 覆盖不冲突 |

**取样数量按项目的耦合面定**，不是越多越好；但**至少要有一个"客户端指令密集"的模组**——否则误拦这一类 bug 在空实例里永远测不出来。

### 8.5.3 必须分清阶段

**构建成功 ≠ 部署成功 ≠ 实机验收 ≠ 已上传。** 报告时逐项声明：

| 阶段 | 可以说什么 | 不可以说 |
|---|---|---|
| 已构建 | "jar 已产出，路径 X，MD5 Y" | "做好了" |
| 已部署待验收 | "已拷进 <实例>，MD5 一致，待实机验收" | "能用" |
| 已验收 | "在 <实例> 上逐项过了 §8.5.1 的清单" | "可以发布了" |
| 已上传 | "File ID = X，页面可见" | — |

**不要把"实例数量"当成"已验收数量"**：装了 10 个实例不代表 10 个都实机跑过。**只有明确实机跑过的才算验收**，其余以项目记录为准，不要"补记"成功。

## 8.6 部署与验收自检清单

**部署前**

- [ ] 目标实例按 §8.2.1 的**前缀**判定通过，且不在 §8.3.1 的禁碰名单里。
- [ ] 加载器按 §8.2.2 的**库坐标**判定，不是靠目录名或 `grep fabric`。
- [ ] 实例真实 MC 版本取自 `<version>.json`，不是目录名（§8.2.3）。
- [ ] 部署三查：版本号来自 `gradle.properties`、产物 mtime 是本次构建、从包内回读过改动。
- [ ] 前置库在实例里且版本落在 `depends` 区间内。
- [ ] 无游戏进程运行（§8.4.4 第 3 条）。
- [ ] `build/libs` 旧 jar 未动（不删 / 不移 / 不备份 / 不记录）。

**部署中**

- [ ] 实例 `mods/` 内同 modId 的旧 jar 已删，只留最新一版。
- [ ] 落地文件名与产物同名，无改名、无加后缀。

**部署后**

- [ ] MD5 回读**逐字符一致**（两个哈希都记下来）。
- [ ] 部署清单（`{实例, 文件名, MD5}`）已出，作为唯一凭据。
- [ ] "已部署到 X，待实机验收"已写进项目记录。

**验收**

- [ ] §8.5.1 的 8 项逐项过，每项都有结论（不是"应该没问题"）。
- [ ] 混装环境里逐个触发共存模组的客户端指令，确认无误拦。
- [ ] 卸载本模组后其余模组仍能进世界。
- [ ] 有资源的改动确认无"数据包错误"弹窗。
- [ ] 报告里的阶段声明准确（已构建 / 已部署待验收 / 已验收 / 已上传，四者不混用）。
- [ ] 缺实例的 `MC × 加载器` 格子已明确标"缺"，没有用相邻实例顶替、没有声称"已验收"。
